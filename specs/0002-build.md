# Building the SDK

`scripts/sdk.py <step> <target>` builds one target, on Linux x86-64 for every target. Its steps, in order, are `checkout`, `packages`, `mac-sdk`, `patch`, `configure`, `build`, `package`, and for a release `sources`. Each is safe to run again on a kept checkout, such as one CI restores from its caches or the runner service resumes (specs/0003-ci-cd.md, Caches): a step that finds its work done does nothing, and a build carries on from what Siso finds. CI keeps the checkout and each build directory as caches of their own, restored apart, and runs `reconcile` first (Reconciling, below). The checkout is at `$LIBCHROMIUM_CHECKOUT` (default `~/libchromium/checkout`) and depot_tools at `$DEPOT_TOOLS` (default beside it).

## Checkout

`chromium/pin.json` names the Chromium release tag and its commit; `checkout` refuses a tag that names another commit. `chromium/gclient` is the checkout's `.gclient`: one checkout serves every target, so it lists `mac` with `linux` and `arm64` with `x64`, which brings macOS's toolchain pieces, Linux's arm64 sysroot and the PGO profiles to a Linux machine. `checkout` fetches the tag, runs `gclient sync` at it with no history, and `gclient runhooks`, and records that it finished for that pin and `.gclient`, so a later run skips it. A checkout at another pin is moved to this one in place, its patches reverted first, so that most files that didn't change keep their times, and a build directory built from the old pin and restored with it rebuilds little more than what changed (Reconciling, below): the patched files and the GN target's copy, which the move deletes as an untracked directory and `patch` makes again, get new times. Its sync passes `--reset`, which discards what a patch left in a dependency, and `-D`, which deletes the dependencies the new pin no longer has, which gclient would otherwise keep for good, though it still keeps some, such as one at a path the new pin ignores that has changes of its own, a git dependency that holds one the new pin adds, or a dropped GCS dependency's files at a path the new pin ignores, and, with `--reset`, the untracked directories that git doesn't ignore in each dependency it moves. Not `--force`, at first: with `-D`, it deletes what `git status` lists after a reset, in `src` every dependency whose commit the move changes, which would all be cloned again with new times. But with `--force` gclient mends some dependencies it can't otherwise bring to the pin, such as one whose `HEAD` is damaged, cloning some of them again, so if the sync fails, `checkout` says so in the job summary and syncs once more with `--force` as well; what that doesn't mend fails the step. `checkout` marks a move from before `src` leaves its pin until its sync and hooks finish, and syncs as for a move while any move is unfinished, whatever pin it was for, so a machine stopped part-way syncs as for a move when it resumes, and a move abandoned part-way is never taken for a finished one; but a stop inside gclient can still leave what it was deleting or writing: the rest of a dropped dependency at a path the new pin ignores, as a sync without `-D` would keep it whole, or a cut-short `.gclient_entries` or `.gcs_entries`, which fails the rerun. A sync at the same pin, for another `.gclient`, with no move unfinished, isn't a move, and passes `--force` alone. `packages` installs Chromium's Linux build dependencies with its own `install-build-deps.sh` on every run, since they live on the machine while the checkout is kept; it never waits for a password.

## Settings

`chromium/args.gn` is the same for every target; `configure` adds the target's `target_os` and `target_cpu` from `targets.json`, and for macOS the Apple SDK's version and the settings a Linux machine needs (below). It writes the build directory's `args.gn` only when it differs, since a newer one regenerates everything, and runs `gn gen` only then, or when the build directory has no `build.ninja`, or may have been generated from another toolchain: when its record of what it's built from is missing or not one `configure` wrote once GN had generated, which say so with `generation` 2 (an earlier `configure` wrote it before, and `reconcile` keeps either), the checkout isn't whole, or the record names another pin or `.gclient`, or a patch that differs from the checkout's where either changes a file in `build/toolchain/`, as when `patch` changes a patch after `reconcile`. Chromium's toolchain scripts are no command's inputs: GN puts their modification times in the commands that run them, such as `TOOL_VERSION` in every macOS link, and reads them only when it generates, to the second: a script changed in the same second as GN last generated would keep its old commands, but a patch is always applied in a later run. It marks the build directory while GN generates, which can leave a `build.ninja` if it fails or is stopped, and generates again while the mark is there; it writes `.libchromium-built-from.json` in the build directory, what the build directory is built from (Reconciling, below), once GN has generated, or when it doesn't need to, and then removes the mark. For macOS, it refuses unless the pinned Apple SDK is installed, and refuses a build directory that holds anything but what `configure` writes and whose record names another Apple SDK, whose files can be older than what was built from the last, or none, unless GN was first generating for it with no SDK recorded: `reconcile` removes such a build directory, as CI's does before `mac-sdk` installs the SDK.

### Reconciling

The checkout's state is what its own records say: the pin and `.gclient` it was synced to, each patch applied, with the files it changes, and the GN target's copy, `src/libchromium`; the same state means the same files, whatever their times. `configure` records it in the build directory, with, for macOS, the Apple SDK installed. A build directory restored apart from its checkout may have been built from another state, whose differing files can be older than what was built from them. `reconcile`, run after restoring both and before any other step, compares the build directory's record with the checkout's state and the pinned Apple SDK: if they match, it does nothing; at the same pin and `.gclient`, it makes the files of each patch that differs, both the one the build directory was built with and the checkout's, and if the GN target's copy differs, its files, newer than anything built, so they rebuild; for anything else, another pin or `.gclient`, a checkout that isn't whole, another Apple SDK than the pinned one, or no record, or one naming any path that isn't plainly relative, it removes the build directory, which is built afresh.

There is one configuration per target, Chromium's release build, which embedders' development and release builds both link, so that what an embedder tests is what it ships, and so that the SDK's flags, which fix `DCHECK_IS_ON()` and every build flag in the headers, are one set:

- `is_official_build = true`, `is_debug = false`, `dcheck_always_on = false`, with PGO and ThinLTO as official builds have them; `symbol_level = 1`, `blink_symbol_level = 1`, `v8_symbol_level = 1`: line tables everywhere, Blink and V8 included, so on Linux a stack through them has its files and lines, inlined calls included. `use_debug_fission = false` keeps all of the debug information in the linked library rather than in split DWARF's `.dwo` files, which the `symbols` part wouldn't hold; on Linux it goes to the `symbols` part, and the library ships stripped. macOS ships no debug information (no dSYMs, no `symbols` part), so the setting only costs its build time.
- `is_component_build = false`: one library, which the patch's `libchromium_exports = true` makes export the component build's API (specs/0001-sdk.md, Exports), with `v8_expose_public_symbols = true` for V8's.
- `libcxx_is_shared = true`: libc++ as a shared library the library and the embedder share.
- `is_component_ffmpeg = true`: FFmpeg as its own shared library; `proprietary_codecs = false`, `ffmpeg_branding = "Chromium"`.
- `is_cfi = false`, `use_cfi_icall = false`: control-flow integrity can't allow calls into an embedder.
- `use_remoteexec = false`.

## The patch

`chromium/patches/` holds the SDK's changes to Chromium, as one patch for each repository it touches, applied by `patch`. It adds the GN argument `libchromium_exports`, which:

- defines `LIBCHROMIUM_EXPORTS` for every target, which every export header that keys its `visibility("default")` on `COMPONENT_BUILD` (PartitionAlloc's, on its own `IS_COMPONENT_BUILD` flag) also takes, so a non-component build's shared library exports what a component build's libraries do;
- builds components as source sets in the target's toolchain, so the library takes each whole, as a component build's libraries do, and keeps every export whether anything in it calls the export or not (a non-component build's static libraries would give the link only the objects something refers to);
- keeps `PRESERVE_MOST` off in base and V8, as in a component build;
- gives V8's thread-locals the model a shared library can hold, as in a component build (Blink's heap has an argument of its own for that, `blink_heap_inside_shared_library = true`, among the settings);
- makes Skia, skcms, Abseil, BoringSSL, Perfetto and V8's platform and base libraries, which choose their exports in GN, export as in a component build;
- gives macOS's shared libc++ the `@rpath` install name a component build gives every library, and leaves the allocator shim's `operator new` and `delete` visible there, as a component build does, to match shared libc++'s declarations;
- gives executables and shared libraries the `$ORIGIN` (or `@loader_path`) run path a component build gives them, since libc++ and FFmpeg are shared libraries here and the build runs executables of its own, such as protoc;
- keeps whole-program vtable optimisation off;
- compiles the two targets that `chromium/gn/BUILD.gn` names for export but which have no export macros, `//components/embedder_support:user_agent` and `//ui/events/blink`, with `-fvisibility=default`, and makes the first, a static library, a source set, so every one of their functions is linked and exported (specs/0001-sdk.md, Exports);
- compiles every mojom target's C++, its generated shared code, its default variant's bindings and the traits sources it compiles itself, with `-fvisibility=default` after Chromium's `-fvisibility=hidden`, keeping inline functions hidden: a component build compiles them hidden into each component that uses them, which would leave an embedder's own mojom that imports one, such as `gfx.mojom.Rect`, without its wire structs or traits (specs/0001-sdk.md, Mojom). Blink's variant is left as it is, and so are traits a separate target compiles;
- and, whatever the argument, lets a macOS build without V8's context snapshot generate: Chrome's own app bundle, which the SDK never builds but GN always loads, lists V8's snapshot without depending on what makes it.

Apart from the argument, it carries one fix the pin doesn't have, whatever the argument: macOS's linker driver (`build/toolchain/apple/linker_driver.py`) writes a shared library's `.TOC`, the list of its exports that decides whether what links it must relink, with a list joined once, rather than by appending to `bytes`, which copies the whole TOC each time. For this library's 310,000 exports that took 11 minutes on one core, after a link of 76 seconds; the TOC is the same either way. It's reported as https://issues.chromium.org/issues/587040685, and Chromium fixed it the same way in commit `394153f1299c` (`refs/heads/main@{#1747697}`). The fix goes when the pin includes that commit; `export_patch.py` stops on a pin that does, because the text its edits replace is gone.

`scripts/export_patch.py <checkout>/src`, run on a clean checkout, writes the patches: one rule for the export headers, outside trees the SDK never links (Chrome, other platforms, tests), and exact edits, each of which must match once, for the GN files and the linker driver. Moving the pin is: change `chromium/pin.json`, check out the new pin, run `export_patch.py`, and review the patches' differences. `patch` applies each patch unless it is applied already, and starts a repository's patched files again from the pin's when a machine stopped mid-step left it half applied.

## Build

`patch` also copies `chromium/gn/` into the tree as `//libchromium`, only where it changed, so a new checkout of this repository rebuilds nothing. `//libchromium` holds:

- `:chromium`, the shared library, whose public dependencies are the exported targets, so a target that depends on it compiles with their settings and links only the library, a shared library being a link boundary;
- `:embedder_probe`, an embedder in miniature that depends only on `:chromium`; it is never run, and its compile and link commands are the flags the SDK ships;
- `:resources` and `:locales`, the resource packs;
- `:libchromium`, everything a package needs, with ICU's data and V8's snapshot.

`build` runs `autoninja` for `:libchromium`. A failed build fails the step.

## macOS

A Linux machine builds macOS with Chromium's clang and `ld64.lld` against Apple's SDK, which Chromium looks for as a hermetic Xcode in `build/mac_files/xcode_binaries`. `targets.json` pins it: the archive's object in the organization's private bucket for CI tools, `gs://lanescape-ci-tools/macos/sdk/26.2/MacOSX26.2.sdk.tar.zst`, and its SHA-256. The bucket is laid out `<platform>/<tool>/<version>/<file>`, with each file's SHA-256 beside it as `<file>.sha256`, and an object in it never changes: a new SDK is a new path, and so a new pin. `mac-sdk --archive <file>` installs a local copy of the archive there, as CI does with the copy its own steps fetched and checked (specs/0003-ci-cd.md, Credentials); without `--archive`, it copies the object with the machine's own Google Cloud sign-in. Either way it checks the archive's SHA-256 against the pin before it uses it, and does nothing if that SDK is installed already. Every install has the same modification times: every file, directory and symbolic link the archive lists its own, wherever a link puts it, the archive's root (`Contents`) included if it lists it, and what isn't in it, the directories it doesn't list and the directories that hold the SDK, the archive's newest. Python's `tarfile` gives a link the time it's made, and GN names SDK files among its own inputs, so a newer one on every install would make GN generate again on every build from a build directory kept in a cache, and so could rerun every macOS link (Settings, above). Its marker, which names the SDK installed, is beside it, `.<place>.libchromium-apple-sdk`, and an SDK is installed only if its marker and `Contents` are both there, so that writing it changes none of the SDK's times; an install removes it first and writes it last, once every time is set, so a stopped install is never taken for a whole one, and the next does it all again. Apple's SDK is only ever on build machines: it is never packaged, published or logged. `configure` names its version for Chromium, and sets `use_system_xcode = false`, `enable_dsyms = false` (nothing on Linux can make dSYMs), and `use_v8_context_snapshot = false` (specs/0001-sdk.md, Runtime files).

## Packaging

`package --version <v> --output <dir>` writes the target's parts (specs/0001-sdk.md, Parts) and `assets-<target>.json`, which describes them. With `--quick`, for CI's tests alone (Quick packages, below), it writes them faster and without `symbols`:

- **Flags.** The probe's compile and link commands, from Siso's build files, become `sdk.json`'s lists. Paths in them become `{sdk}/include/…` (the source tree), `{sdk}/gen/…`, `{sdk}/sysroot`, `{sdk}/lib/…` or `{apple_sdk}`; any other path stops the packaging, so no build machine's path ships.
- **Headers.** The roots are the headers of every target the library links whose directory is part of the public surface (`HEADER_ROOTS` in `scripts/package.py`, and every `//services/*/public`), source and generated, and V8's `include/`. Each root is preprocessed alone with the SDK's flags, or, if that fails, after `build/build_config.h`, which some of Chromium's headers use without including, and every file any of them includes ships, from the source tree into `include/` and from the build into `gen/`. A root that doesn't preprocess alone, such as another platform's, is left out, and its count is in `sdk.json`. The list is collected afresh every time: it depends on every header's contents and on which files exist in the source tree and the build's `gen/`, where an earlier build can leave files behind, and no key short of those captures it. The set is complete for every root, and holds nothing they don't include, except Chromium's libc++, libc++abi and libc++'s configuration, which ship whole, since an embedder may use any standard header.
- **Mojom** (specs/0001-sdk.md, Mojom). Mojo's base types' generated sources join the header roots, for what any generated bindings' sources include beyond their headers, such as `mojo_buildflags.h`, and so does every header the type mappings name, such as a traits header that only generated sources include; a mapping that names a header the SDK doesn't then ship is dropped from `type_mappings.json` if its type's name starts with none of the namespaces that the importable mojoms' parsed modules reach, their own or that of any type they hold, through fields, parameters and imports, since then no embedder's bindings can use the type; otherwise, or if a reachable module has no namespace, it stops the packaging. Every mojom whose `.mojom.h` ships also ships the headers the generator writes beside it for the default variant (`MOJOM_COMPANIONS`), which an embedder's generated bindings include for an import, and what they include, until no further mojom's `.mojom.h` joins; a mojom one of whose companions the build doesn't have, or that doesn't preprocess with the SDK's flags, isn't importable, and ships neither of the next two. The tools' libraries' licence files (`MOJOM_LICENCES`) must be among what ships, or the packaging stops. Every other such mojom also ships its `.mojom` source, into `include/`, or into `gen/` if the build generated it, and the module the build parsed it into, into `gen/`; a mojom whose bindings ship without either stops the packaging. The type mappings of every mojom target the library is built from, but for Blink's variant, which maps the same types to Blink's own, are merged into `mojom/type_mappings.json`; a type mapped two ways stops the packaging. Chromium's bindings generator, its parser and the libraries they import (`MOJOM_TOOLS` in `scripts/package.py`) ship into `mojom/` as the checkout has them, without their unit tests, and the features the build parsed Mojo's base types with become `sdk.json`'s.
- **Libraries** are copied, their debug information kept in `symbols/` on Linux, and stripped; the stripped library names its debug information by `.gnu_debuglink`.
- **Toolchain.** Chromium's clang, `lld` and the LLVM tools an embedder's build uses, clang's own headers, and the target's runtime libraries.
- **Notices** (specs/0004-licences.md).

Archives are deterministic: entries sorted, times, owners and modes fixed, compressed with zstd at level 19, on every core. Nothing in the environment changes a release's level. A part of 2 GiB or more fails the step. `sources` writes the corresponding source (specs/0004-licences.md) and `assets-sources-<target>.json`.

### Quick packages

CI's package goes only to its own embedder and test jobs, is kept a day and is never published (specs/0003-ci-cd.md, CI), so `--quick` makes it faster: zstd level 3 instead of 19, and no `symbols` part, which neither the embedder nor the test uses. Its libraries are still stripped and linked to their debug information by `.gnu_debuglink`, exactly as a release's are, so CI tests the same library; only the debug information itself isn't archived. Level 3, zstd's default, compresses far faster than 19, and smaller than level 1 at no measurable cost, so less to upload and download: a macOS `libchromium.dylib` of 217 MiB becomes 63 MiB at level 19, 79 MiB at level 3 and 90 MiB at level 1.

A quick package never reaches a release. `package` refuses `--quick` for any version but a pull request's, `<tag>-pr<number>`, which is never published; it marks each quick part `"quick": true` in `assets-<target>.json`; and `publish.py`'s `manifest` and `release` each refuse any part so marked, and any version missing any part of any target in `targets.json` (`package.parts_of()`), `symbols` included. `.github/actions/build` asks for `--quick` only when its `release` input is `false`, and `scripts/check.py` requires CD's calls of the chain to pass `release: true` and CI's to pass only their target.

## By hand

On a Linux x86-64 machine with about 250 GB free, for one target:

```
export LIBCHROMIUM_CHECKOUT=$HOME/libchromium/checkout
for step in checkout packages mac-sdk patch configure build; do python3 scripts/sdk.py $step linux-amd64; done
python3 scripts/sdk.py package linux-amd64 --version 157.0.8103.39-dev --output out
```

For macOS, `mac-sdk` needs a Google Cloud sign-in that may read the bucket, or `--archive <a local copy>` of the pinned archive.
