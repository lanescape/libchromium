# The SDK

An SDK version is upstream Chromium at one release tag, built with this repository's settings and patch as one shared library that exports the Content API, and packaged for each target with what an embedder needs to compile its own code against it and link it: headers, generated ones included, the exact flags, and Chromium's own toolchain and, on Linux, sysroot. An embedder never compiles Chromium. The SDK is for any Content API embedder and knows nothing of any one of them.

## Versions

A version is `<Chromium tag>-<revision>`, such as `157.0.8103.39-1`, published as the GitHub release tagged `v157.0.8103.39-1`. A push to main publishes its newest commit as the next revision of its pin, unless a newer push's run has published first (specs/0003-ci-cd.md, CD and Versions), so a change to the pin, the settings, the patch, the packaging or the scripts ships in a new version, and so does a change to nothing that reaches the binaries. Versions are not semver and promise no compatibility with each other, not even between two revisions of one tag: an embedder pins an exact version and moves by changing it. A published version never changes.

Targets are `linux-amd64`, `linux-arm64` and `macos-arm64` (`targets.json`).

## Parts

Each target's SDK is a set of parts, each a deterministic `.tar.zst` asset of the release, which extract into one directory, the SDK's root:

| Part | Asset | Holds |
|---|---|---|
| `lib` | `libchromium-<version>-<target>-lib.tar.zst` | `lib/`: `libchromium.so`, `libc++.so` and `libffmpeg.so`, or on macOS `libchromium.dylib`, `libc++_chrome.dylib` and `libffmpeg.dylib`; `resources/`: the runtime files; `sdk.json`; `args.gn`; `notices/` |
| `headers` | `…-headers.tar.zst` | `include/`: source headers, laid out as in Chromium's tree; `gen/`: generated headers, as in the build's `gen` directory; with each shipped mojom's `.mojom` source in `include/`, or in `gen/` if Chromium's build generated it, and parsed module in `gen/`, and `mojom/`: Chromium's mojom bindings generator and its type mappings (Mojom, below) |
| `toolchain` | `…-toolchain.tar.zst` | `toolchain/`: Chromium's clang and LLVM tools, their own headers and the target's runtime libraries, built for Linux x86-64 |
| `sysroot` | `…-sysroot.tar.zst` | Linux only. `sysroot/`: Chromium's Debian sysroot for the target |
| `symbols` | `…-symbols.tar.zst` | Linux only. `symbols/`: each library's debug information, which the stripped library names by `.gnu_debuglink` |
| `notices` | `…-notices.tar.zst` | `notices/`, as in `lib` (specs/0004-licences.md) |

The release also holds the corresponding source (specs/0004-licences.md), `manifest.json`, which lists every asset with its size and SHA-256 and says where Chromium's own source is, which the release points to rather than copies, and `SHA256SUMS`. A release asset can't be 2 GiB or larger, and CD fails, naming the asset, before it publishes one that is (specs/0003-ci-cd.md, Publishing).

Libraries ship stripped: Linux ones of everything but their dynamic symbols, macOS ones of their local symbols, and signed ad hoc again by the stripping. A macOS SDK ships no debug information, since a Linux build can't run `dsymutil`.

## sdk.json

`sdk.json` describes the target: everything a build tool needs to compile and link an embedder, with no GN. Paths are absolute once two placeholders are replaced: `{sdk}`, the SDK's root, and, on macOS, `{apple_sdk}`, the path of the embedder's own Apple SDK (`xcrun --show-sdk-path`, or a copy). A GN-free JSON file fits any build tool, a `build.rs` with the `cc` crate as well as CMake or a script, where a GN or CMake export would fit one.

| Field | |
|---|---|
| `schema` | 1. A change that an existing reader would misread is a new number |
| `version`, `target`, `system`, `cpu`, `chromium` | The version, target, `linux` or `mac`, `x64` or `arm64`, and the pin (`tag`, `commit`) |
| `clang` | The toolchain's clang version and Chromium's revision of it |
| `toolchain` | `cc`, `cxx`, `ar`, `nm`, `strip`, `objcopy`, `linker` |
| `sysroot` | `{sdk}/sysroot` on Linux, `null` on macOS |
| `defines` | Preprocessor definitions, without `-D` |
| `include_dirs`, `system_include_dirs` | In order, for `-I` and `-isystem` |
| `compile` | Every other compile flag, in order, by language: `c++`, and on macOS `objective-c++` |
| `link` | `flags`, then `libraries` (the SDK's to link: `libchromium` and `libc++`), `system_libs` (for `-l`) and `frameworks` |
| `mojom` | `parser`, `generator`, `imports` (the roots of the shipped `.mojom` sources, `{sdk}/include` and `{sdk}/gen`), `modules` (the root of their parsed modules), `type_mappings`, and `features`, the features Chromium's build parsed Mojo's base types with (Mojom, below) |
| `runtime` | `libraries` to ship beside the embedder, and `resources` (paths relative to the root) |
| `apple_sdk` | macOS only: the Apple SDK and Xcode the SDK was built with |

The flags are the ones Chromium's own build uses for a target that depends on the library, read from the compile and link commands of an embedder in miniature that the build makes for the purpose (specs/0002-build.md, Packaging). They leave out what is Chromium's own business: warnings, optimisation, debug information, profiles, LTO, Chromium's clang plugins and where the binary finds its libraries. An embedder adds its own of those, and its own include path, and must not change what the SDK's flags define: the defines, language standard, `-fno-exceptions` and the libc++ flags are part of the library's ABI. `DCHECK_IS_ON()` and every build flag are fixed by the version.

An embedder compiles with the SDK's clang, `{sdk}/toolchain/bin/clang++`, which runs on Linux x86-64; the macOS SDK's is the same, and cross-compiles. Building on a Mac needs Chromium's clang for macOS of the same revision (`clang.revision`), which the SDK doesn't ship.

## Exports

The library exports what Chromium's component build exports between its components: every class and function marked with Chromium's export macros (`CONTENT_EXPORT`, `BLINK_EXPORT`, `COMPONENT_EXPORT(...)` and the rest) in what it links, which covers the Content API and the base, UI, Blink public, Mojo, URL, network, media, GPU, Skia, V8, PartitionAlloc, Perfetto, Abseil and BoringSSL APIs those reach. That is the surface Chromium's own embedders, such as `content_shell`, use across component boundaries every day, so an embedder that builds as a component of Chromium links against the SDK. The library is built from Chromium's targets listed in `chromium/gn/BUILD.gn`; what isn't marked for export, or isn't linked, isn't available, and the other third-party libraries Chromium links (ICU, protobuf, the codecs and the rest) aren't exported: an embedder that needs one brings its own, and must keep its symbols apart from Chromium's. One more thing is exported that a component build keeps hidden: the C++ of every mojom target, its generated code and the traits sources it compiles itself, but for Blink's variant, such as `gfx.mojom`'s, which a component build compiles into each component that uses it, so that an embedder's mojoms can import any mojom whose bindings ship (Mojom, below). Inline functions stay hidden, as Chromium builds them. And two targets the list of targets names for embedders but which have no export macros are exported whole: `//components/embedder_support:user_agent`, Chrome's user agent and client-hint brands (`embedder_support::GetUserAgent()` and the rest), and `//ui/events/blink`, which turns UI events into Blink's (`ui::MakeWebMouseEvent()` and the rest). Chromium builds without component-build exports otherwise, so the SDK carries one patch (specs/0002-build.md, The patch).

The library is otherwise Chromium's release build: official, with PGO and ThinLTO, without DCHECKs. Two optimisations that assume the link sees the whole program are off, because an embedder implements Content's interfaces (`ContentBrowserClient`, `WebContentsDelegate`, …) in its own binary: control-flow integrity, which would stop every call from the library into the embedder, and whole-program vtable optimisation, which would devirtualise calls to interfaces it believes it sees all of. `[[clang::preserve_most]]` is off too, as in a component build, since a lazily bound call to an exported function would clobber the registers it keeps. Linking with `-z now`, as the flags do, binds every call at load.

## Mojom

An embedder whose browser and renderer talk over interfaces of their own, as `content_shell` does, defines them in mojom, Chromium's language for messages between processes, and generates their C++ bindings with Chromium's generator. The SDK ships what that needs, in the `headers` part: the generator, its parser and the libraries they import, in `mojom/` as Chromium has them; for every importable mojom, its `.mojom` source, in `include/`, or in `gen/` for the few Chromium's build generates, and the module Chromium's build parsed it into (`<name>.mojom-module`), in `gen/`, so an embedder's mojom imports them, such as `mojo_base.mojom.String16` or `gfx.mojom.Rect`, by the same paths as in Chromium; and `mojom/type_mappings.json`, which maps Chromium's mojom types to their C++ classes, such as `gfx.mojom.Rect` to `gfx::Rect`, for the default variant (not Blink's), with every header those mappings name. A mojom is importable when its C++ bindings ship with every header the generator writes beside them for the default variant that an importer's bindings include (`MOJOM_COMPANIONS` in `scripts/package.py`; not its test utilities); one any of whose headers can't ship ships no source or module, so importing it fails at once, by name. The library exports every such mojom's generated code (Exports, above), so an embedder compiles only its own mojoms' bindings. Each needs Python 3.

An embedder's mojom links when every type it uses from Chromium's has its traits inline, exported, or compiled by its own mojom target, as `mojo_base.mojom`'s, `gfx.mojom`'s and `ui.mojom.ImeTextSpan`'s are. Traits that a separate target compiles keep that target's own visibility: exported where it names an export macro, as `mojo_base.mojom.String16`'s do, and hidden otherwise, such as `media.mojom.OverlayInfo`'s, in `//media/mojo/mojom:shared_mojom_traits`; a mojom that uses a type of the hidden kind doesn't link. Such a target is exported by name in the patch (specs/0002-build.md, The patch) when an embedder needs it.

In outline, with `sdk.json`'s `mojom` paths, an embedder's source root `<src>`, its mojoms under it, and an output directory `<gen>`:

```
python3 <parser> --input-root <src> --input-root <each of imports> --module-root <modules> --output-root <gen> \
  --mojoms <each mojom's absolute path> --enable-feature <each of features>
python3 <generator> -o <templates> --use_bundled_pylibs precompile -g c++
python3 <generator> --use_bundled_pylibs -o <gen> generate -d <src> -I <src> --bytecode_path <templates> -g c++ \
  <extra> <the mojoms>
```

The last runs three times, with `<extra>` `--generate_non_variant_code`, then `--generate_non_variant_code --generate_message_ids`, then `--typemap <type_mappings>`, writing `<name>.mojom.h`, `<name>.mojom-shared.h` and the rest under `<gen>`, and their sources, `<name>.mojom.cc` and `<name>.mojom-shared.cc`, which the embedder compiles with the SDK's flags and `-I<gen>`. `tests/embedder/build.py` does exactly this for the test embedder's `probe.mojom`, and is the reference.

## The C++ library

The Content API passes `std::` types across its boundary, so an embedder uses Chromium's libc++ (namespace `std::__Cr`), never its system's: its headers ship in `include/` and the flags select them (`-nostdinc++`). It is its own shared library, `libc++.so` (on macOS `libc++_chrome.dylib`, apart from the system's), which the library and the embedder both link, so a process has one copy of its globals and type information. An embedder's binary must not also contain another C++ standard library; Rust's standard library, which isn't C++, is unaffected.

## The allocator

Chromium's allocator, PartitionAlloc, is in the library with its malloc shim, as in Chromium's own builds. On Linux the shim's `malloc`, `free`, `operator new` and the rest are the library's exports, and replace the C library's for the whole process when the library is loaded at startup: an embedder links it, and never loads it with `dlopen`, which would leave memory from two allocators in one process. An embedder doesn't define those functions itself, nor link another allocator that does. On macOS the shim installs itself as the default malloc zone when the library loads.

## FFmpeg

FFmpeg is LGPL 2.1, so it is its own shared library, `libffmpeg`, which the library loads by its name from beside it. A user may replace it with one built from the published source (specs/0004-licences.md). Proprietary codecs are off.

## Runtime files

`runtime.libraries` and `runtime.resources` go beside the embedder's executable, where Chromium looks by default (`base::DIR_ASSETS`), or wherever the embedder tells Chromium to look:

- From `lib/`: the libraries the library loads, as GN lists them among its runtime dependencies: `libc++`, FFmpeg, ANGLE's `libEGL` and `libGLESv2`, SwiftShader (`libvk_swiftshader`, with its Vulkan driver manifest `vk_swiftshader_icd.json`) and the Vulkan loader (`libvulkan`). Not ANGLE's mock Vulkan driver or Vulkan's validation layers, which are for testing.
- `resources.pak`: Content's, Blink's, the network stack's and the UI's resources, at 100% scale, which every process loads (`ui::ResourceBundle::AddDataPackFromPath`).
- `locales/<locale>.pak`: Blink's and the UI's strings, one for each locale Chromium ships.
- `icudtl.dat`: ICU's data.
- On Linux, `v8_context_snapshot.bin`, V8's snapshot with Blink's contexts in it. On macOS, `snapshot_blob.bin`, V8's own snapshot: a context snapshot is made by running a build of the target, which a Linux machine can't do for macOS, so the macOS SDK is built with `use_v8_context_snapshot = false`, and a renderer makes its first context without a snapshot.

Content runs its child processes by running the embedder's executable again with `--type=`, so the executable passes its arguments to `content::ContentMain`. As in `content_shell`, the embedder serves Content's resources and strings through its `ContentClient` (from `ui::ResourceBundle`), and installs the process's `display::Screen` before it creates a `WebContents`: `aura::ScreenOzone` with Aura on Ozone, `display::ScopedNativeScreen` on macOS.

### Linux

The library loads the system libraries in `readelf -d libchromium.so`'s list, such as GLib, NSS, D-Bus and the X11 libraries, which an embedder's users install from their distribution (`tests/embedder/debian-packages.txt` names Debian's). Chromium's Ozone chooses X11, Wayland or headless at runtime. The sandbox needs unprivileged user namespaces; the SDK doesn't ship Chromium's setuid sandbox helper.

### macOS

The SDK ships no app bundles. An embedder's executable serves every process, as on Linux: it must create an `NSApplication` that implements Content's `CrAppProtocol`, `CrAppControlProtocol` and `NativeEventProcessor` before Content's browser main runs, and enter the sandbox from its `main` with `sandbox::SeatbeltExecServer::CreateFromArguments` before anything else, as `tests/embedder/platform_mac.mm` does. An embedder that ships signed helper apps with entitlements of their own makes them itself. Apple's SDK is never part of a version: an embedder builds with its own, passed as `{apple_sdk}`.

## Compiling and linking

In outline, with `{sdk}` and `{apple_sdk}` replaced:

```
<toolchain.cxx> -x c++ <compile.c++> -D<defines> -I<include_dirs> -isystem <system_include_dirs> <the embedder's flags> -c a.cc -o a.o
<toolchain.cxx> <link.flags> a.o <link.libraries> -l<link.system_libs> -framework <link.frameworks> -Wl,-rpath,<where the libraries are> -o embedder
```

`tests/embedder/build.py` does exactly this, and is the reference. In a Rust `build.rs`, the same lists go to `cc::Build` (`.compiler()`, `.flag()`, `.define()`, `.include()`) and to `cargo:rustc-link-arg`, with the linker set to the SDK's clang.
