# CI, CD and releases

The workflows in `.github/workflows/` check, build, test and publish through the scripts in `scripts/`. `startup.yml` runs what every target's chain starts from: the checks that need no Chromium, and the Chromium checkout job, which saves the checkout the builds restore; `target.yml` is one target's chain, its build, embedder and test jobs; `ci.yml` runs on pull requests to main and `cd.yml` on pushes to main, and each calls `startup.yml` once and `target.yml` once for each target. The chain's jobs share their steps through `.github/actions/build` and `.github/actions/embedder`.

## Machines

Every target compiles on the organization's runner service, `lanescape/runners`, through its actions, `lanescape/runners/actions/<name>@v1`, on `lanescape-80vcpu-linux-amd64-spot`: macOS is cross-compiled there too. The builds alone use that machine. Every target's test embedder is built on `lanescape-16vcpu-linux-amd64`. Each target is tested on a machine like it, as `targets.json`'s `test_runner` names it: `linux-amd64` on `lanescape-16vcpu-linux-amd64`, `linux-arm64` on `lanescape-16vcpu-linux-arm64`, and `macos-arm64` on Blacksmith's `blacksmith-6vcpu-macos-26` (`scripts/check.py` keeps `target.yml` the same). The Chromium checkout job runs on `lanescape-16vcpu-linux-amd64`, an `amd64` machine like the builds', since caches are kept by architecture. The checks and CD's version and publish jobs run on `lanescape-2vcpu-linux-amd64`. Nothing else uses Blacksmith or GitHub's hosted runners, except a fork's pull request: the service makes no machines for forks, and a fork can't build Chromium on GitHub's runners, so a fork's run does only the checks, on `ubuntu-26.04`: the Chromium checkout job runs only if the run isn't a fork's pull request, and `ci.yml` calls each target's chain only if the pull request's head repository is this one.

A job names its selector alone in `runs-on`, as the service requires, and sets its machine up in its own steps.

## Caches

Compiling Chromium is the expensive part. A build job, and the Chromium checkout job when it makes the checkout, asks for its work disk, which the runner service gives it empty, mounted at `/work`: 150 GB, room for the checkout and a build directory, which together have come to at most 58 GB, with 10,000 IOPS and 2,400 MiB/s, since moving their many small files in and out of caches is bound by the disk's operations, and takes three times as long at the service's default, 3,000 IOPS. A Hyperdisk Balanced disk's size, IOPS and throughput are each paid for, and at 150 GB it allows up to 75,000 IOPS, 500 for each GB, and with 10,000 IOPS provisioned, up to 2,400 MiB/s, a quarter of its IOPS, so the smaller disk keeps the same performance; and keeps what's slow to make again as caches, which `.github/runners.json` declares and only `target.yml`'s build and `startup.yml`'s Chromium checkout job restore and save, with the service's actions `cache` and `save-cache`. Nothing else uses a work disk or a cache: the checks, the test embedder's build, the tests and publishing set their machines up in their own steps and download what they need, such as the packaged SDK, as workflow artifacts from the build job, and save nothing; the corresponding source's Debian downloads go to the job's temporary directory. There are two kinds of cache, and only the build's output is saved every time:

- **`chromium-checkout`**, shared by every target, holds `/work` as the Chromium checkout job leaves it: depot_tools (`/work/depot_tools`) and the checkout (`/work/chromium`), synced and patched, with the records `scripts/sdk.py` keeps there. Its key is exactly `chromium/pin.json`, `chromium/gclient` and the patches, which decide its files but for the GN target's copy, which `patch` refreshes in every build and `reconcile` compares (below), so the saved checkout is a starting point that every build brings up to date: the checkout is saved patched, and patching again after a patch changes touches files, so a changed patch makes a new key. `startup.yml`'s Chromium checkout job alone saves it, once for each key. When the checkout for the run's key isn't saved, the job restores the newest there is and brings it up to date with `scripts/sdk.py checkout` and `patch`, which are the same for every target, as one `.gclient` brings every target's dependencies, and which leave most unchanged files their times (specs/0002-build.md, Checkout), so that a build directory built from the older checkout rebuilds little more than what changed; then it saves it, leaving out `lost+found` and the file that marks its work disk (below). It learns whether the checkout for the run's key is saved by asking the `cache` action to check it, `check-only: true`, which downloads nothing and records no choice, so that the run's first restore of the checkout still chooses: if a restore would come from a version for the run's key (`_exact`), the job does nothing more. Otherwise it asks for its work disk, restores the checkout, brings it up to date and saves it, each step with `if: steps.needed.outputs.make == 'true'`. The builds never save it: the macOS build adds the Apple SDK to its checkout, and no cache may hold the Apple SDK, which this way none can.
- **`chromium-out-<target>`**, one for each target in `targets.json`, holds that target's build directory, `/work/chromium/src/out/<target>`, restored into the checkout. Its key is everything that decides what the target's build compiles: the pin, `.gclient`, settings, every file of the GN target, the patches, `targets.json` and `scripts/sdk.py`, which writes the build's arguments, so the same key means the same inputs. Every build saves it, after its build.

`scripts/check.py` keeps every key complete, and the steps that restore and save them as above. The service saves a cache only from a job that succeeds, and chooses the version a run restores once for each cache, the first time one of the run's jobs asks, so every target's build in a run restores the same checkout: for its key, else its newest whatever the key, first in the run's own scope and then in main's. The builds need the Chromium checkout job, so they ask after it has finished. If the checkout for the key was saved already, the job only checked it, and the builds restore that one. If it wasn't, the job's own restore fixed the run's choice to whatever it found, usually an older checkout, so the builds restore that same one, and bring it up to date as the job did, each in its own checkout and patch steps, and later runs of the key in that scope restore what the job saved, once the service has made it ready. Either way every build in a run starts from the same checkout. The check answers from the same restore order as the builds' restore, but at its own moment: a version that becomes ready, or goes, before the builds restore can make them choose another, which they bring up to date the same way. So the check is a snapshot, and a checkout that ends up wrong for its key, as when a rerun of a run from before this job saves an older one, is made again by the first later run whose check no longer finds a version for its key. A build says in its job summary when the checkout it restored isn't for its key, or when there was none. All builds run on `amd64` machines, macOS's too, so every target shares that architecture's caches. The build steps check what they find and rebuild only what's out of date: a checkout of another pin is synced to the pin, which leaves most unchanged files their times (specs/0002-build.md, Checkout), and another patch is reverted and the new one applied, which leaves files that come out the same their times; the caches keep every file's time to the nanosecond, so with the checkout restored, then its build directory, the build is incremental.

The two caches are chosen apart, so a build directory can have been built from another state of the checkout than the one restored, as when a pull request's own newest build directory meets main's newer checkout, and the files that differ can be older than what was built from them. So `configure` records in the build directory what it is built from, and after restoring both the build runs `scripts/sdk.py reconcile`, which makes the files of each patch that differs, and the GN target's copy, newer than anything built, so they rebuild, and removes the build directory, so that it's built afresh, if it was built from another pin or `.gclient`, from a checkout that isn't whole, or for macOS against another Apple SDK than the pinned one (specs/0002-build.md).

- **main** restores main's caches, and saves main's: every successful CD build saves its target's build directory, so main's are always those of its newest build, and the Chromium checkout job saves the checkout for a key main hasn't saved.
- **A pull request** restores its own, else main's, so its first build compiles only what it changed relative to main's newest build, and later pushes only what changed since. It saves its own, which go when it closes, and never main's.

The first run after the caches replace work disks finds none, and builds cold. A cold build, with no caches, can outlast one machine: the service stops a job at 90 minutes, or a Spot machine is preempted, and reruns the job, up to 3 attempts of the run in all, on a work disk made from the job's resume image, where the steps carry on. Every build job's name is unique for that reason: `Build <target>`, in a call named for its target, so GitHub shows it as `<target> / Build <target>`. A build writes `/work/.libchromium-restored`, with where its checkout came from, once it has restored and reconciled its caches; a rerun that finds it restores nothing, so it carries on from its resume image rather than going back to the caches, which would undo the lost job's work. A rerun that doesn't find it restores and reconciles again. A Chromium checkout job lost the same way is rerun on its own resume image. It writes `/work/.libchromium-restored` before it syncs, so the rerun finds it and doesn't restore the checkout again over the lost job's work, and `checkout` and `patch` carry on. A work disk without it holds at most a restore cut short, which the job clears before it restores, so that no two versions of the checkout are ever mixed. The rerun checks again, and does nothing more only if that check now finds a version for the key; an automatic rerun keeps its run's restore choice, if the lost job made one, so it usually carries on making and saving the checkout.

## CI

On a pull request, `ci.yml` runs startup, the checks and the Chromium checkout job side by side, then builds all three targets and tests each on its machine. A new push cancels the run in progress (`concurrency` with `cancel-in-progress`). A failed compile, package or test fails its job; a skipped job is only ever a fork's, or one after a failure.

Each target is a chain of its own, `target.yml`, called with the target: **Build** → **Embedder** → **Test**, each needing the one before, and every chain needing startup. A failure stops its own chain and no other: no job starts once a job before it in its chain has failed, and no chain starts if the checks or the Chromium checkout job fail. The other targets' chains carry on, so one push still shows every target that builds and passes.

- **Checks** (`startup.yml`), needing no Chromium: the scripts' tests (`tests/scripts`), the repository's checks (`scripts/check.py`: every script compiles, the pin is well formed, `.github/runners.json` declares the checkout's cache and one build directory's for each target, with their keys, only `target.yml`'s build and `startup.yml`'s Chromium checkout job have a work disk and caches, the build saves its build directory every time and never the checkout, the build restores the checkout and its build directory unless it resumes, the Chromium checkout job checks the checkout, and only when it makes it restores it, unless it resumes, brings it up to date with `checkout` and `patch`, and saves it, on an `amd64` machine, the runner service's actions are named by their tag, `lanescape/runners/actions/<name>@v1`, and every other action is pinned to a commit, the build and the Chromium checkout job ask for their work disks as below, the Apple SDK the workflows fetch is the one `targets.json` pins, the workflows' shape and permissions (below), every artifact is kept 1 day, README lists every spec), and `actionlint` over the workflows, configured by `.github/actionlint.yaml` with the runner labels it can't know.
- **Chromium checkout** (`startup.yml`), beside the checks: saves the checkout for the run's key, if it isn't saved already (Caches, above).
- **Build**, for each target, on its work disk: restore the caches, check that the checkout and patches are in place, configure and build Chromium, and package the SDK, which goes to the next job as the artifact `sdk-<target>`. A pull request's package is a quick one, at zstd level 3 and without `symbols`; CD's is whole, at level 19, and only a whole one is ever published (specs/0002-build.md, Quick packages). Artifacts belong to the run, and calls of `target.yml` share their caller's, so each target's names are its own in the run, and CD's publish job finds every target's. A pull request's version is `<Chromium tag>-pr<number>`, which is never published. Whether the compile passes or fails, the build then writes to its job summary why Siso ran what it ran, from Siso's own record of this build, `siso_explain` in the build directory, which the build removes first since the cache brings the last build's (if it can't, the build runs with Siso's record turned off, unexplained): how many entries the record has, and the commonest reasons, counted by the directory of the input that made each step run, so a restored cache that rebuilds more than it should says why. It counts the first 1,000 kinds of reason, and says how many entries had others. The summary holds only fixed words and those directories, and nothing in the report can fail a build or replace a failed one's error. Once the build has handed its package on, the whole record is kept as the artifact `siso-explain-<target>`, a step like any other, which runs only if everything before it passed; if the upload fails, the build job fails, before it saves its caches, and its chain stops there.
- **Embedder**, for each target, on a fresh `lanescape-16vcpu-linux-amd64` with no Chromium checkout: extract the package's `lib`, `headers`, `toolchain` and `sysroot` parts into an empty directory and build the test embedder there with `tests/embedder/build.py`, with nothing but the SDK's toolchain, `sdk.json` and its mojom tooling, which generates the bindings of the embedder's own `probe.mojom` (and for macOS, the Apple SDK, which this job fetches as an embedder would bring its own). The embedder, with the runtime files beside it, goes to its own target's test machine as the artifact `embedder-<target>`.
- **Test**, for each target: run the embedder (`tests/embedder/test.sh`), which installs the system libraries Chromium loads on a Linux machine, starts Content with its sandbox, loads a page whose script computes a value, reads the value back through JavaScript in an isolated world, asks the page's renderer for the page's title and a rectangle over `probe.mojom`, an interface of the embedder's own associated with the frame's channel, checks Chrome's user agent and the conversion of a mouse press into Blink's, which the SDK exports without export macros, and exits 0 only if all of them are right, within 3 minutes.

**Artifacts are intermediate**, and every one, in CI and CD, is kept for 1 day (`retention-days: 1`, which `scripts/check.py` requires of every upload), as a resume image can resume a job for a day. A rerun more than a day later, of a failed test or of CD's publish job alike, finds its run's artifacts gone, and the whole run must be rerun, which rebuilds. CD's publish job refuses unless every target's `sdk-<target>` is there, so a rerun of it alone never publishes fewer targets than `targets.json` names. Releases are not artifacts, and never expire (Publishing, below).

The macOS build and the macOS embedder job alone sign in anywhere but GitHub, to fetch the Apple SDK (Credentials, below). Every other job but CD's publish job (Publishing, below) has `contents: read` at most.

A called workflow's jobs get their token from the job that calls it, and can narrow but never widen it. So `ci.yml` and `cd.yml` grant each call `contents: read`, and the `macos-arm64` call alone also `id-token: write`. In `target.yml`, the build and the embedder set no permissions of their own, and get their call's grant; the test sets `contents: read`, so not even macOS's has `id-token`. A job of `target.yml` can't ask for `id-token: write` itself: GitHub refuses a called job that asks for more than its call grants, and the Linux calls grant no `id-token`. As a backstop, a Linux target's build and embedder fail at their first step if they could ask for an OIDC token. `scripts/check.py` keeps this shape: each workflow calls `target.yml` once for each target in `targets.json`, and every call grants exactly the above and needs startup, and in CD the version job, and nothing else, so no chain waits on another; CI has no jobs but startup and the calls, which skip forks; `startup.yml` has the checks, which always run, and the Chromium checkout job, which needs nothing, so the two run side by side, and runs for every run but a fork's pull request, and in CD only for a commit that publishes; CD's calls run only if the version job says the commit publishes, and CD's publish job needs every call; the chain is build → embedder → test, and neither its jobs nor the publish job set a condition of their own, so each runs only if every job it needs succeeded; nothing runs past a failure (`continue-on-error`, `always()`, `cancelled()` or `failure()`); only the build runs on `lanescape-80vcpu-linux-amd64-spot`, and the test on its target's `test_runner`; `startup.yml`, `ci.yml` and `cd.yml` grant nothing by default, and every job has exactly `contents: read` but the calls of `target.yml`, CD's publish job (`contents: write`), and `target.yml`'s build and embedder, which set no permissions and take their call's grant, as `target.yml` sets none for the whole workflow; and `.github/actions/apple-sdk` is used only by `target.yml`'s build and embedder, in a step whose own condition limits it to `macos-arm64`. It reads the workflows and actions line by line, so it refuses YAML it couldn't read as GitHub does: anything but plain keys directly followed by their colon, each level indented 2 spaces more than its parent, with plain or one-line quoted values, `{}`, flat flow sequences or block scalars, and no anchors, aliases, tags, merge keys or flow mappings.

## Credentials

The macOS build and the macOS embedder job each copy the pinned Apple SDK (specs/0002-build.md, macOS) onto their machine with `.github/actions/apple-sdk`, which hard-codes the archive's object, `gs://lanescape-ci-tools/macos/sdk/26.2/MacOSX26.2.sdk.tar.zst`, and its SHA-256 (`scripts/check.py` keeps both the same as `targets.json`'s), and checks the copy's SHA-256 before anything uses it. It is a step of their own in `target.yml`, which runs only for `macos-arm64` and hands the archive to `.github/actions/build` or `.github/actions/embedder`. They sign in to Google Cloud with GitHub's OIDC token, through workload identity federation, so those two jobs alone have `id-token: write`, from the `macos-arm64` call's grant (CI, above). The provider and the account are fixed in the action, and aren't secrets: the provider `projects/168731703350/locations/global/workloadIdentityPools/lanescape-ci-tools/providers/github`, which must accept only tokens from the `lanescape` organization's repositories, and the service account `lanescape-ci-tools-reader@lanescape-dev.iam.gserviceaccount.com`, which must be able only to read the objects of `gs://lanescape-ci-tools`, the organization's one private bucket of platform tools for every repository's CI. The organization's infrastructure makes the bucket, the pool and the account, not this repository.

The runner service plays no part in this: its machines are plain Debian 13, and the job fetches the SDK itself. A fork's pull request never runs these jobs (Machines, above), so it never signs in. Nothing logs the credentials, and the archive stays in the job's temporary directory: it is never in an artifact, a package or a release.

## CD

On a push to main, `cd.yml`:

1. **Version**: decides the version before anything builds, so the packages and manifest carry it (Versions, below), and writes it, or why there is none, to the job summary.
2. **Startup**, the checks and the Chromium checkout job, as in CI, once the version is decided: the Chromium checkout job runs only if the version job says the commit publishes (`startup.yml`'s input `checkout`), so a rerun of an older commit, which publishes nothing, never replaces main's checkout with its own. A rerun of only an older run's failed jobs, after a newer commit has published, reuses that run's version decision, so its Chromium checkout job, like its builds' build directories, can replace main's caches with its own until a later run on main whose check no longer finds a version for its key makes them again; Publish still refuses to release it.
3. Each target's chain, **Build** → **Embedder** → **Test**, as in CI, once startup passes and only if the version step says the commit publishes, with the version; the build also writes the corresponding source (specs/0004-licences.md) into its artifact.
4. **Publish**, needing the version, startup and every target's chain: checks the version is still the next and that every target's artifact is there (CI, above: artifacts are kept a day), gathers every target's assets, checks every part of every target is there, none is a quick package and every corresponding source is there (specs/0004-licences.md), writes the manifest and publishes the release (Publishing, below). If any target's chain fails or is skipped, nothing is published.

CD runs once for each push to main, for the push's newest commit, and releases that commit, so a push of several commits releases only the last, which holds the changes of those before it. Its runs go one at a time, each in its turn, in the order they began to wait, and none is cancelled, waiting or running (GitHub's `concurrency` with `queue: max`), so the runs publish in the order they began to wait, each that passes and whose commit no newer release holds, up to GitHub's 100 waiting, past which it cancels the newest; then the maintainer reruns that run once the queue has room. A commit without a release of its own ships in the next one released, and that run's job summary lists the commits on main's first-parent line since the previous release that weren't released on their own: with squash merges, that is every one. A run that publishes nothing, because its commit isn't newer than every released commit, succeeds and says why: so does an older push's run that began to wait after a newer push's, or is rerun after a newer one has published, and its commit ships in the newer release. The version job and the publish job each fetch the tags and the whole history, which the ancestry checks need, and fail if they can't: `version.py main` refuses a shallow history, whose missing commits could make it skip a release it should publish.

## Versions

A version is `<Chromium tag>-<revision>` (specs/0001-sdk.md, Versions), and its release's tag is `v<version>`. Nothing in the repository records a revision; `scripts/version.py main` derives it from the tags:

- The revision is the highest revision of any `v<Chromium tag>-<n>` tag for the commit's pin, plus one, or 1 if there is none. Every commit that publishes (below) gets one, including one that changes nothing the binaries are made from: its binaries match the previous version's, and that is intended.
- A commit publishes only if it is a strict descendant of every release tag's commit, newer than everything released. A rerun of an older run therefore publishes nothing, and never ships older content as a newer revision. A revert that restores older inputs is a new commit, so it gets a new revision: versions only move forward.

## Publishing

`scripts/publish.py` is the one interface to the releases: `gather` merges the jobs' assets, refusing two jobs' different copies of one asset; `manifest` writes `manifest.json`, which lists every asset with its size and SHA-256 and, under `source`, where the source is that the release points to rather than copies (specs/0004-licences.md, Corresponding source), and `SHA256SUMS`, and fails, naming the asset, if any asset is 2 GiB or larger; `release` publishes. `manifest` and `release` both refuse a version that lacks any part of any target, holds a quick one, or lacks any corresponding source or holds one that isn't whole (specs/0004-licences.md). Releases are on GitHub, as GitHub releases of this repository, holding each version's binaries, notices and corresponding source together. A release's notes say where its source is: the `source-*` assets, and, as in the manifest, Chromium's source tarball and its checksums, the Chromium tag and commit, and this repository's patch at the release's tag and commit.

`release` refuses if Chromium's source tarball for the pin or its checksums file isn't published, which it asks for without credentials, so that a release never points to source that isn't there; then it refuses if the version's tag exists or a published release for it does, deletes a draft for the version that a failed run left, creates a new draft, uploads every asset, trying each up to 3 times whether GitHub refused it or the connection dropped, checks each uploaded asset's size and SHA-256 against the manifest, and only then publishes the draft, which creates the tag at the commit last, and checks the tag names the commit. A failure before that leaves a draft, which is never visible as a release. It never changes or deletes a published release or a tag. Only the publish job has `contents: write`, with the workflow's own `GITHUB_TOKEN`; nothing logs the token, or any URL an upload or download is given: when a request fails, the log has only the method, the URL's path, and GitHub's status or the kind of failure, never what GitHub answered. The token goes only where it's sent, to GitHub, never on with a redirect, as when checking an uploaded asset by downloading it, if GitHub doesn't report its SHA-256. An upload whose answer is cut short or empty is tried again too.

Every version stays published. GitHub keeps releases and their assets until someone deletes them, so retention is the maintainer's to set: the design assumes at least 3 years, as the licences' source offers need, and no automation deletes a release. GitHub's immutable releases setting, where available, stops anyone changing a published release or its tag, and is a backstop the maintainer can turn on.
